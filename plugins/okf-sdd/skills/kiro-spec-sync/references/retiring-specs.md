# 旧仕様の削除と置換

仕様変更・実装後の同期、または古い仕様の整理で読む。
現行本文は、今も有効な要件・契約・実装計画を示す。
変更のたびに旧仕様を積み重ねる保存場所にはしない。

## 削除を決める根拠

対象の各記述を、維持、置換、削除、判断待ちに分類する。
ユーザーが採用した変更、決定記録、該当差分と検証結果を照合する。
新規 feature に同じ責務を移した場合も、旧 feature と関連 steering を影響先に含める。

| 状況 | 処置 |
|---|---|
| 許可済みの新しい要件・契約が旧記述を置換する | 旧記述を本文から除き、現行の記述に置き換える。 |
| 要件や機能の撤回が確定している | 要件・受け入れ条件と、それだけを実現する設計・タスクを削除する。 |
| 同じ現行契約が複数箇所に重複している | 責務を持つ正本へ統合し、他は必要な参照にする。 |
| 承認済み機能が未実装、または実装が要件に違反する | 要件を保持し、未完了または不具合として扱う。コードに合わせて削除しない。 |
| 新しい案が未採用、または置換範囲が不明 | 現行の確定事項を保持し、判断が必要な箇所だけ保留する。 |

古い日付、完了した `[x]`、未参照、コードに存在しないことだけを削除根拠にしない。
有効な完了タスクや継続中の制約は残す。
撤回ではなく別仕様へ責務を移す場合は、移管先に有効な要件・契約・未完了作業があることを確認する。

## 本文と参照を一緒に整理する

1. 旧要件ID、契約名、旧名称、対象外条件、文書パスを検索し、削除対象と影響先を絞る。現在の Git 差分だけでなく、置換元の既存仕様も読む。
2. sync の規則で意味変更の承認を先に失効させ、未反映の影響先を `needs-sync` に記録する。
3. 旧要件と専用の設計節・図・API例・タスクを削除または置換する。「以前は…」や打消し線で現行本文へ残さない。共用部分は有効な責務へ書き換える。削除した要件ID・タスクIDを別の意味に再利用しない。
4. brief、roadmap、steering、他仕様の本文、リンク、`sources`、`kiro.depends_on` を更新する。名称だけ差し替えず、新契約との意味の一致を確認する。古い制約が残る対象外の節も確認する。
5. research の現行要約も置換する。既存の変更記録へ、削除したID・契約、根拠、理由、置換先（撤回なら置換なし）を短く残す。詳細な旧本文は Git 履歴を使う。Decision は経緯として失効と置換先を明記し、現行の指示から切り離す。
6. 旧ID・旧契約と削除パスを再検索する。残存箇所が有効な互換性要件または明示的な履歴だけか確認する。削除要件に対応する実装・テストの処置も判断するが、文書保守の依頼だけでコード削除や期待値緩和を行わない。
7. 影響した親子タスク、生成状態、承認、ready を再評価し、索引を再生成する。意味を確認した存続仕様だけ snapshot と check を行う。未解決の影響先があれば `NEEDS_SYNC` のまま返す。

確認できない参照を、リンク検査を通すためだけに消さない。
依存契約が未解決なら、存続する所有仕様の `pending` に対象パスと理由を残す。

## 文書・feature 全体が不要になった場合

一部の記述の失効と、feature 全体の廃止を区別する。
有効な要件、未完了作業、契約依存が残る feature は、古い部分だけを整理する。
全責務の撤回または移管が確定し、逆参照を解決できた場合は、依頼された同期・整理の範囲で不要な文書や feature ディレクトリを削除できる。
無関係なユーザー変更は削除しない。

継続して参照する経緯が必要なら、旧文書を全文保存せず、既存の決定記録か短い `status: deprecated` の案内に理由と置換先を残す。
廃止した feature を保持する場合は、その `spec.json` の全承認と `ready_for_implementation` を false にし、`generated` は残存ファイルの有無に合わせる。
deprecated は Markdown の状態であり、spec.json の phase に未定義の廃止値を追加しない。
索引に案内が載る場合も現行仕様と誤認されない説明にする。
feature を全削除する場合は、その制御ファイルも削除し、存続側の参照・確認記録と共有索引を更新する。削除した feature の snapshot は実行しない。

## 判断例

- 許可済みの保存先変更：旧保存先を指示する要件・設計・タスクと「新保存先は対象外」を置換する。新保存先がまだ未実装でも、採用済みの要件を消さない。
- 未採用の保存先変更案：旧仕様を保持する。`--check` は置換候補と必要な判断を報告するだけで、削除・snapshot・状態更新をしない。
- 新 feature への移管：旧 feature の全責務と未完了タスクを照合する。一つでも移管されていなければ全削除せず、その部分を維持または pending にする。
- 旧コードを削除しただけの変更：要件撤回の根拠がなければ不具合として扱う。試験を削除して仕様充足を主張しない。
