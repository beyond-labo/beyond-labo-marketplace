# 共通の配置、責務、契約

App、Backend、UNIX の設計時に、命名、境界、実装範囲を判断するための共有資料。
このプラグインが共通原則の正本を所有し、プラットフォーム固有の API と検証は専用スキルが所有する。

## 原則とプロジェクトの選択

最初に既存コード、ローカル規約、決定記録を読む。
確定した方針、提案、古い文書の記述を区別し、矛盾を新しい決定として転記しない。
依存を内側へ向ける原則と、フォルダー名の選択を区別する。
[Clean Architecture 原典](https://blog.cleancoder.com/uncle-bob/2012/08/13/the-clean-architecture.html)は Interface Adapters に Controller、Presenter と外部データの変換を含める。
Presentation や Infrastructure という名前を必須の層名として指定してはいない。
実行時に外部を呼ぶことと、ソースコードが外部の型へ依存することは別に示す。

## この配布物の命名既定

以下は Beyond Labo の新規設計向け既定であり、言語一般の規則ではない。
対象プロジェクトの明示ルール、言語とツールの制約を優先し、既存コードの一括移動はリファクタリングの範囲に含まれる場合だけ行う。

- ソースルート直下を `<Feature>/<Layer>` とし、`features/<Feature>` や `Features/<Feature>` を挟まない。
- 機能、層、役割は PascalCase / UpperCamelCase とする。役割は `UseCase`、`Port`、`Mapper`、`View`、`Reducer` などの単数形にする。
- 「camelケース」という指定を受けても、`UseCase` の例なら UpperCamelCase と解釈したことを明記する。lowerCamelCase と混同しない。
- 例は `src/Hosting/Application/UseCase/CreateHosting`、`src/Hosting/Domain/Model/Hosting`。役割ディレクトリは実在する責務の整理に使い、全種類を揃えない。
- `apps/backend`、`apps/ios`、`src`、`docs` などの配置用ディレクトリ、`package.json` などの規定ファイル、npm/pnpm の識別子は変更対象外。
- `Manager`、`Helper`、`Util` のように所有者を隠す名前を避ける。名前の接尾辞を揃えるためだけに型を追加しない。

## 役割の区別

| 役割 | 所有する責務 | 増やさないもの |
| --- | --- | --- |
| UseCase | 業務操作とその調整 | HTTP エンドポイントごとの機械的な中継クラス |
| Port | 内側の呼び出し側が必要とする契約。通常 Application、業務概念自体が要求するときだけ Domain | SDK の API を丸写ししたインターフェース |
| Adapter | 外部の形式や操作を内側の契約に接続する実装。入力側と出力側を区別 | 名前だけの Repository / Gateway ラッパー |
| Repository | モデルの保存や取得をコレクションとして扱う契約または実装 | あらゆる外部 HTTP 接続の総称 |
| Gateway | 外部サービスへの接続を表す役割。Port と実装のどちらを指すか明記 | 受信 HTTP と送信処理を混ぜる層 |
| Mapper | 特定境界での値、形式、失敗の変換 | 横断 DTO 変換層、全型共通の変換プロトコル |

HTTP は通信方式、Port は契約、Gateway は接続の役割であり、層名と同列に並べない。
Adapter が Repository の Port を実装する場合、一つの実装が両方の役割を担える。
Store はフレームワークにより意味が異なるため、永続化 Store と UI 状態を駆動する Store を区別する。

## 外部契約とモデルの所有

Domain のモデルはアプリごとに所有する。
独立リリースするアプリ間では、`packages/contracts` 等のソース共有で内部型や API DTO を直接 import しない。
この配布物の既定は Backend 所有の HTTP スキーマから OpenAPI を生成し、利用側が固定した契約成果物から自身のクライアントを生成する流れとする。
既存の schema-first 方式等を採用済みなら、依頼範囲外で生成方向を反転させず、正本と生成物の関係を記録する。

Backend は実装との整合と公開契約の互換性を検証する。
利用側は契約の版またはハッシュ、生成ツールの版と設定を固定し、通常ビルドで稼働中サーバーの最新スキーマを取得しない。
Backend の変更だけで iOS のビルド入力を変えず、独立ビルドと独立リリースを保つ。
旧 iOS の存在を前提に、削除、必須化、意味変更、enum 追加、デコーダーの未知値処理を旧クライアントでも検証する。
契約差分の検査だけで実際の後方互換性を保証したと報告しない。

変換は外部契約を知る機能の境界が所有する。
単純で一か所だけの変換は Adapter の private 関数から始め、複雑化や独立テストの必要に応じて Mapper へ分ける。
Domain の型に生成 DTO を受け取る initializer を置かない。
表示用の整形は Presentation が所有するが、層ごとに同形の DTO を複製する必要はない。

共通の通信基盤と生成クライアントが必要なら `Platform/Networking/Generated` を使える。
Platform は機能のモデルを知らず、生成型は通信基盤と機能の API Adapter / Mapper に閉じ込める。
Domain、Application、UI の状態や Action に生成型を流さない。
アプリ内の shared kernel も、複数機能が実際に使う安定した契約に限定し、所有者と依存の循環を確認する。

## 実装範囲と検証の区別

YAGNI を適用し、実際の処理に必要な最小の型とファイルだけを作る。
空の層や型、コメントだけのソース、無効な OpenAPI、開けない Xcode プロジェクト、未選定ツールのダミー設定、必ず失敗する予約 CI は追加しない。
将来の配置は文書に記載し、例のツリーを一括生成しない。

現存する処理に対して検証を行う。
ファイル配置や設定の構成検証、契約検証、単体テスト、アプリビルド、実行時検証を分けて報告する。
実行環境や処理が未実装なら、その検証は未実施とする。
フォルダーの分離では import 制約を強制できないため、実装に応じて import 検査やモジュール境界で確かめる。
実効性のある制約が必要になるまで、ビルドパッケージを層ごとに量産しない。
