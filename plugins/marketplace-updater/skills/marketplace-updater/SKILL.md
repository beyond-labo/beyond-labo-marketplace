# Marketplace Updater

利用中のスキルで見つかった問題を、確認した配布元のソースへ反映する。
今いるリポジトリを配布元と仮定せず、問題の整理から修正、検証、許可済みの PR 作成まで同じタスクで進める。

## 依頼の対象と到達点

- 直前の会話から、対象スキル、起きた問題、期待する振る舞いを抽出する。分かっている内容を聞き直さない。
- 「この問題が起こらないように $skill-name で改善して」は、文脈にスキルの不備や再発防止の意図がある場合、スキル自体の改善として扱う。「$skill-name でこの記事を改善して」は、そのスキルを使った成果物の修正として扱う。
- 修正対象の解釈が結果を変えるほど曖昧な場合だけ、対象を絞る質問をする。通常の利用や単発の実行失敗から、配布元変更の許可を推定しない。
- 「このタスク中は、見つかったスキルの不備を修正してドラフトPRまで進めて」のような継続許可があれば、その範囲内で再確認せず進める。許可を他のタスクへ自動で拡張しない。
- PR 作成の依頼には、必要なコミットと push を含む。修正だけの依頼ではローカルで検証済みの差分を用意し、公開の許可が必要なら具体的な差分と PR 案を示してから確認する。

## 配布元の確定と作業場所

最初に [配布元の特定手順](references/source-resolution.md) を読み、次を結び付ける。

1. 実際に使用された `SKILL.md` とそのバージョン。
2. 所有するプラグインの manifest と、インストール元マーケットプレイスのエントリー。
3. 修正対象リポジトリ、プラグインの相対パス、スキルの相対パス。

同名スキルを名前だけで選ばない。
解決した配布元と対象を短く伝えてから作業する。
元の作業リポジトリのブランチと未コミット変更を保持し、インストール済みキャッシュやマーケットプレイスのスナップショットを編集しない。

Git 配布元が確定したら、そのリポジトリ専用の作業コピーで進める。
既存の開発用 checkout が確認できれば再利用し、作業中の変更がある場合は独立した worktree または clone を選ぶ。
checkout がなければ、現在の作業リポジトリの外にある書き込み可能な専用ディレクトリへ clone する。
サンドボックスの制限に当たったら必要な実行承認を求め、別のツールで迂回しない。

配布元の `AGENTS.md` を読み、ユーザー指定のベースブランチを優先する。
指定がなければリモートの既定ブランチを確認して fetch し、取得したコミットから新規ブランチを作る。
常に `main` とは限らない。取得に失敗したら、古い参照を最新と報告しない。
Git 操作には `git-branch-workflow` が利用できれば使う。
利用できない場合も、確認したリモートへの fetch、新規ブランチの作成、ベース SHA の記録は通常の Git で行える。
Git コマンドには作業コピーを `git -C` または実行ディレクトリで明示する。
GitHub CLI のリポジトリ操作には、確認した配布元を `--repo` で指定し、利用元プロジェクトの現在位置に依存させない。

## 根拠のある改善

配布元の最新ソースと、実際に使われたバージョンを比較する。
最新ソースですでに解決していれば、重複修正を作らず取り込み状況と更新方法を報告する。
認証切れ、ツール不足、対象プロジェクト固有のバグ、指示の読み落としを、スキルの欠陥と混同しない。

スキルの変更では、利用できる `skill-creator` を使う。
プラグインの構成変更では `plugin-creator` を使う。
必要なスキルが利用できなければ配布元の規約と検証手順を読み、満たせない必須チェックを報告する。
この Updater の導入だけで、他のプラグインや CLI が自動導入されるとは扱わない。

- `plugins/` の説明、トリガー、入出力を比較し、既存の責務に収まる最小の修正を選ぶ。
- 同じ注意書きがすでにある場合は、重複追記よりもトリガー、参照導線、矛盾する指示を調べる。
- 問題が起きた条件と期待する行動を一般化する。利用元のコード、会話全文、組織情報、秘密値、端末固有のパスを配布物や PR へ転記しない。再現例には合成データを使う。
- manifest、カタログ、公開ドキュメントを配布元の規約に従って同期する。カタログ用の公式 scaffold が指定されている場合はそれを使う。
- 実装上必要な変更だけを行い、他のスキルへの一律の制約追加や、利用元プロジェクトの設定変更へ広げない。

## 検証と公開

配布元の validator と、変更に対応する実行チェックを行う。
指示を変更した場合は、問題が起きた依頼と、引き続き通常動作すべき近い依頼の両方で判断の整合を確認する。
スクリプトを変更した場合は、関係する挙動を実行して確かめる。
validator 成功、手順の机上確認、モデルによる実行試験を区別し、実行していない確認を成功と書かない。

公開の許可がある場合は `gh-pull-request-workflow` が利用できれば使う。
利用できない場合は、Git と認証済みの `gh` で対象ファイルだけをコミットして作業ブランチを push し、確認した配布元とベースを明示してドラフト PR を作る。
PR 本文は一時ファイルへ書き、`--body-file` で渡す。
既存 PR が同じ変更を扱っているかを確認し、再試行による重複を避ける。
作成後は URL、head、base、ドラフト状態を読み戻す。
merge や自動マージの設定は、この改善フローに含めない。

認証不足や権限不足では、作成済みの差分と PR 案を保持し、失敗した段階と必要な操作を伝える。
アカウントの切り替え、権限の変更、fork の作成を勝手に行わない。
接続エラーを「PR 作成済み」と扱わない。

## 配布と利用中タスクへの反映

ソースの修正、PR の作成、配布への取り込み、インストール済み版の更新は別の状態である。
PR を作っただけで、現在のタスクや他の利用者へ修正が反映されたと報告しない。

- Git 配布元から導入した場合は、修正が配布ブランチに取り込まれた後、確認したマーケットプレイスの更新と対象プラグインの再インストールを案内する。
- ローカル開発版を試す依頼がある場合だけ、`plugin-creator` のキャッシュ更新手順と、対象ソースを参照することが確認できたローカルマーケットプレイスを使う。Git 配布の登録を無断でローカル版へ差し替えない。
- 新しいインストール状態の検証は新しいタスクで行う。現在の問題を直す依頼もあれば、今回の会話では修正した判断を適用して続ける。

最後に、対象と原因、変更内容、実施した検証、作業コピーの場所とブランチ、ベース SHA、PR の URL または未公開の状態、利用環境への反映状況を簡潔に報告する。
