# UNIX Design Principles

UNIX固有のCLI慣習ではなく、保守・変更・統合に強いシステムを設計するための原則として適用する。既存の制約、利用者体験、性能、信頼性を確認し、機械的な細分化は避ける。

## 進め方

1. 対象の目的、利用者、主要ユースケース、品質要件、既存の制約を確認する。
2. コンポーネント、依存関係、データ境界、失敗経路を短く可視化する。情報が不足するときは、妥当な前提を明記する。
3. 下の原則を使い、問題を「責務」「境界」「合成」「運用」「進化」の観点で評価する。
4. 変更案ごとに、期待効果、トレードオフ、移行順序、検証方法を示す。不要な分割・抽象化は提案しない。
5. 設計判断を、少なくとも「なぜここで分ける／分けないのか」「どの契約を安定させるのか」「どの失敗を隔離するのか」で説明する。

## 適用原則

1. **単一の明確な責務を持たせる。** モジュール、サービス、関数、画面、ジョブごとに主目的を一つ定める。新しい目的は、既存要素への機能継ぎ足しではなく、独立可能性をまず検討する。
2. **小さく、単純で、読み解ける形に保つ。** 実装・API・設定・運用手順の概念数を抑える。例外やオプションの増加は、基本モデルの不足を疑う契機にする。
3. **部品を合成可能にする。** 単体で完結する万能部品より、明確な入出力を持つ部品を安全に接続できるようにする。再利用は共通化そのものではなく、安定した接続から得る。
4. **境界を契約として設計する。** API、イベント、スキーマ、コマンド、権限、タイムアウト、冪等性、失敗時の意味を明示する。内部実装を漏らさず、契約の変更は互換性と移行を伴わせる。
5. **相互運用性と可搬性を優先する。** 特定UI、実行環境、ベンダー独自仕様への固定を避ける。標準的で自動処理しやすいインターフェースと、交換・移行しやすいデータ形式を選ぶ。
6. **データを第一級に扱う。** データモデル、所有者、ライフサイクル、整合性、来歴を明確にする。複雑さを必要に応じてデータに表現し、制御フローや暗黙状態に隠さない。
7. **メカニズムとポリシーを分離する。** 汎用的な実行能力と、業務ルール・テナント設定・運用判断を分ける。ポリシー変更でコア実装まで変えずに済む形を選ぶ。
8. **透明で観測可能にする。** 入出力、状態遷移、依存先、重要な意思決定を追跡できるようにする。構造化ログ、メトリクス、トレース、監査記録を、運用上の問いに対応させる。
9. **診断・回復しやすく失敗させる。** 失敗を分類し、利用者・呼出元に意味のあるエラーを返す。影響を局所化し、リトライ可否、補償、タイムアウト、劣化動作、復旧手順を設計する。
10. **早期に小さく試す。** 高リスクな仮説、契約、性能、利用者フローは、最小プロトタイプまたはスパイクで検証する。不自然な設計は、例外を重ねずに作り直す。
11. **拡張性は実際の変化点にだけ設ける。** 将来の利用者・統合先・機能追加に備えて境界とバージョン戦略を持つ。ただし、根拠のない抽象化、プラグイン機構、設定項目は増やさない。
12. **人間の時間と既存知識を尊重する。** 実行資源だけでなく、開発、レビュー、調査、運用、オンボーディングのコストを最適化する。利用者の既知の概念・慣習から不必要に逸脱しない。
13. **操作経路を閉じ込めない。** GUIだけを唯一の経路にせず、必要に応じてAPI、インポート／エクスポート、Webhook、スクリプト等を提供する。自動化と統合を安全に可能にする。

## 分割・統合の判断軸

分割を提案するのは、次のうち複数が成り立つ場合に限る。

- 変更理由、リリース頻度、所有チーム、スケール特性、障害境界、セキュリティ境界が明確に異なる。
- 入出力と整合性責任を、単純で安定した契約として表現できる。
- 個別にテスト、配備、監視、ロールバックする価値が、通信・運用の追加コストを上回る。
- 分割後も、利用者の一貫した体験と、エンドツーエンドの可観測性を維持できる。

次の状況では統合を優先する。

- 常に同時変更・同時配備され、同一トランザクションまたは低遅延の強い整合性を必要とする。
- 境界がデータ構造のコピーやチャット的な呼び出しにしかならず、独立した意味を持たない。
- チーム規模・運用成熟度に対して、ネットワーク、認証、監視、障害対応の負担が過大になる。

初期段階では、モジュラーモノリス内の明確な境界を第一候補にする。独立配備は、実証済みのスケール、信頼性、組織上の必要があるときに選ぶ。

## 注意点

- 「一つのこと」はコード行数ではなく、変更理由と責任のまとまりで判断する。小さすぎる関数・サービス・UIは、認知負荷と結合を増やす。
- 「テキスト／フラットファイル」は歴史的な手段である。現代では、型安全なスキーマ、効率、機密性、検索性、移行性を満たす表現を選ぶ。
- 合成可能性は利用者体験を犠牲にする理由ではない。外部には統合された製品体験を提供し、内部の責務を整える。
- 小さな部品の分散は、性能低下、部分障害、分散トランザクション、監視・認証・バージョニングのコストを生む。マイクロサービス化を目的にしない。
- 単純さは機能不足や安全性の軽視ではない。正確性、セキュリティ、アクセシビリティ、法令・契約要件を満たす最小の設計を選ぶ。
- 早期プロトタイプは本番品質を意味しない。検証後に、セキュリティ、性能、障害回復、移行、運用を明示的に仕上げる。

## 出力の型

レビューでは、重要度順に「観察 → 原則 → 推奨 → トレードオフ → 検証」を記載する。新規設計では、責務表、境界・契約、データ所有、失敗時の振る舞い、段階的な実装・移行計画を含める。根拠のない分割や抽象化は、採用しない理由も明記する。
